# Canonical Data Model

This document defines the v1 domain model. The physical database is PostgreSQL, but the domain boundaries are intentionally provider-neutral.

## Core entities

### Athlete

`athletes` stores identity and stable profile attributes such as timezone and physical profile. Training capacities that change over time are revisioned separately.

### Capacity revision

`capacity_revisions` stores time-effective values such as max HR, resting HR, LT1/LT2 HR and threshold paces. This lets historical analysis use the values that were valid at the time rather than silently rewriting history.

### Zone set and zones

A `zone_set` represents a versioned zone definition for a sport and target type. Individual `zones` store ordered lower/upper bounds and units. Zone sets have effective dates and source metadata so a future lactate retest can create a new set without destroying the old one.

### Workout and workout steps

A `workout` is the canonical structured workout definition. It has a stable UUID and monotonically increasing `version`.

`workout_steps` form an ordered tree. A step can be a normal execution step or a repeat container with child steps. Duration and target semantics are explicit rather than encoded in free text.

Supported v1 duration types:

- `time`
- `distance`
- `open`

Supported v1 target types:

- `none`
- `heart_rate`
- `pace`
- `cadence`
- `power`

`open` is permitted in the model because some legitimate workouts require a manual Lap press, but the QA engine must reject accidental use where automatic advancement was intended.

### Training plan and plan item

A `training_plan` is a reusable/versioned plan. `plan_items` point to workouts using relative `day_offset` plus optional local start time. Applying a plan to a start date creates concrete calendar items.

This deliberately separates reusable plan arithmetic from real calendar dates.

### Calendar item

`calendar_items` are concrete scheduled sessions with explicit timestamps and timezone. They point to the canonical workout and record the workout version that was scheduled.

Status is local and authoritative. Typical states are `planned`, `completed`, `skipped`, `canceled` and `superseded`.

### Activity

An `activity` is a completed training event. It always receives a Paul's Running UUID. It may be linked back to a calendar item, but imported activities are valid even if no planned item exists.

The normalized summary is stored in first-class columns, while provider-specific or not-yet-normalized data can be retained in JSON. Original FIT/source-file metadata is retained so analysis can be rerun as parsers improve.

### Equipment

`equipment` represents shoes, watches, sensors or other gear. `activity_equipment` provides the many-to-many link from completed activities.

### External reference

`external_references` maps a local entity to a provider-specific identifier. It is deliberately separate from the domain tables.

Example:

`calendar_item UUID -> provider=intervals_icu -> external_id=i123456`

The external ID can disappear or be replaced without changing the local UUID.

### Sync job

`sync_jobs` is the durable integration queue and audit trail. It records connector, entity, operation, state, attempts, idempotency key and errors.

The canonical entity is written before a sync job is created. This enforces the rule that an external service cannot become the system of record by accident.

### Sync cursor

`sync_cursors` holds provider-specific webhook or polling continuation state. It is integration state, not training state.

### Audit event

`audit_events` records meaningful changes made by a person, AI client, connector or system process. This is required for safe AI write access and for explaining why a plan changed.

## Relationship overview

```text
Athlete
  |-- CapacityRevision
  |-- ZoneSet -- Zone
  |-- TrainingPlan -- PlanItem -- Workout -- WorkoutStep
  |-- CalendarItem -----------/
  |       |
  |       +-- Activity -- ActivityEquipment -- Equipment
  |
  +-- ExternalReference
  +-- SyncJob
  +-- AuditEvent
```

## Stable identity and versioning

- UUIDs are generated by Paul's Running.
- Workouts and plans use integer versions starting at 1.
- Mutation APIs use optimistic concurrency through an expected version.
- Calendar items store the workout version scheduled at that time.
- Changes that materially alter an already-synced workout should create a new version and a new sync operation rather than mutating provider state without a local record.

## Time handling

- Database timestamps are stored as UTC `timestamptz`.
- Athlete timezone is stored as an IANA timezone, initially `Europe/London`.
- Calendar display and local planned time are derived from the athlete timezone.
- Relative plan items use `day_offset` and local time; applying the plan is the only operation that converts them into actual timestamps.

## Provider independence

No core table should contain an `intervals_*`, `garmin_*` or other provider-specific column. Provider mappings and payload fragments live in integration tables only.
